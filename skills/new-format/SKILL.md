# Мастер нового формата

Новый формат — это два скилла: ред-политика (правила текста) и оркестратор (процесс). Руками их собирают по docs/add-content-type.md; этот скилл делает то же через интервью.

## Шаг 1: Интервью

Задавай вопросы группами по 2-3, не все сразу. Не переходи к генерации, пока нет ответов на все обязательные вопросы:

1. **Название формата** — одно слово латиницей для имени скилла (например, letter, lesson, post). Возьми из аргумента, если передан.
2. **Что это за текст и для кого?** Читатель, его ситуация, результат после прочтения.
3. **Откуда исходник?** Готовый файл (как essay/guide), сбор фактуры исследованием (как overview) или данные о сервисах (как article)? Это определяет, нужен ли шаг исследования и какой агент его делает.
4. **Структура.** Какие блоки обязательны, в каком порядке, что запрещено. Сколько примерно блоков.
5. **Обращение к читателю.** Императив (как в гайдах), модальность (как в статьях), от первого лица, без обращения?
6. **Типичные ошибки.** Что в этом формате чаще всего получается плохо? Это пойдет в проверку плана и финальную проверку.
7. **Есть ли примеры?** Если да — попроси положить их в examples/[формат]/ и предложи после настройки прогнать style-profile.

Ответы «не знаю» допустимы: тогда бери разумное значение по умолчанию из ближайшего существующего формата и помечай его в сгенерированных файлах комментарием «уточнить после первого прогона».

## Шаг 2: Сгенерируй профиль формата

Создай в корне заполненный профиль content-type-[формат].md по шаблону templates/content-type-profile.md — из ответов интервью. Это контракт формата: когда использовать, вход, выход, глубина, нужно ли исследование, где человек утверждает результат. Ред-политика и оркестратор ниже должны ему соответствовать, а не заменять его.

## Шаг 3: Сгенерируй ред-политику

Создай skills/redpolicy-[формат]/SKILL.md по образцу существующих:

- frontmatter: name, description с «что + когда использовать + НЕ для» и ссылками на соседние форматы, user-invocable: false;
- отсылка к good-writing в начале: «Общие правила письма — в скилле good-writing. Ниже только специфика формата»;
- разделы: суть подхода, структура, особенности стиля (из ответа про обращение), проверочные вопросы (из ответа про типичные ошибки);
- в конце — ссылка на examples/[формат]/.

Не переноси в ред-политику универсальные правила письма — они уже в good-writing.

## Шаг 4: Сгенерируй оркестратор

Создай skills/write-[формат]/SKILL.md по образцу write-essay (самый компактный):

- frontmatter: name, description с ожидаемым входом, disable-model-invocation: true, argument-hint;
- первая инструкция — «Общий процесс описан в skills/pipeline-core.md»;
- в параметры формата включи строку «Профиль формата: content-type-[формат].md» — оркестратор передает его агентам;
- разделы-вставки: параметры формата, исследование (нужно/не нужно, каким агентом), проверка плана — специфика, требования к writer, финальная проверка — специфика.

Разделы-вставки заполняй из ответов интервью. Пустых разделов не оставляй: если специфики нет, напиши «специфики нет, действуют общие проверки».

## Шаг 5: Заверши настройку

1. Добавь формат в docs/repository-map.md.
2. Создай папку examples/[формат]/ и напомни положить туда 2–5 эталонов; предложи затем прогнать style-profile.
3. Покажи пользователю все три файла целиком и спроси, что поправить.
4. Если скиллы системы скопированы (а не слинкованы) в папки раннера вроде .claude/skills/ — напомни скопировать туда и новые скиллы, иначе раннер их не увидит.
5. Напомни про smoke-прогон: первый запуск нового формата сделать на черновом исходнике и после него прогнать learn, чтобы добрать правила, которых не хватило.
